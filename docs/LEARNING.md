# 세 단계로 배우는 암호 통신

[프로젝트 소개로 돌아가기](../README.md)

먼저 실행 창과 브라우저를 열고 **프로토콜 실습** 화면을 확인하세요. 아래 실습은 같은 PC 안의 Alice·Bob·Eve 프로세스로 진행됩니다. 예측한 결과를 메모한 뒤 실제 실행 기록과 비교하면 이해하기 쉽습니다.

## 1. 작은 수로 같은 비밀을 만들기

**목표:** 보내는 공개값과 보내지 않는 개인 지수를 구분하고, 서로 같은 공유 비밀을 계산하는 과정을 따라갑니다.

1. DH 계산 모드를 **작은 수 · 수학 학습**, 통신 시나리오를 **정상 통신**으로 선택합니다.
2. 응용 메시지에는 간단한 인사말을 입력하고 **실험 시작**을 누릅니다.
3. **작은 수 계산값 공개**를 누르고 Alice와 Bob의 값을 비교합니다.
4. 기록 재생을 일시정지하고 이전·다음 버튼으로 공개값 교환, 공유 비밀 계산, 세션키 유도 단계를 살펴봅니다.

이 모드의 고정 예제는 다음과 같습니다.

| 값 | Alice | Bob |
|---|---|---|
| 공통 매개변수 | p = 23, g = 5 | p = 23, g = 5 |
| 개인 지수 | a = 6 | b = 15 |
| 공개값 | A = 5⁶ mod 23 = 8 | B = 5¹⁵ mod 23 = 19 |
| 공유 비밀 | S_A = 19⁶ mod 23 = 2 | S_B = 8¹⁵ mod 23 = 2 |

패킷 검사기에서 공개값은 그대로 숫자 `8`이나 `19`로 보이지 않습니다. 이 실험에서는 **사전 공유키 K_AB로 공개값을 암호화해서 교환**하기 때문입니다. 개인 지수 a와 b는 상대 프로세스로 보내지 않습니다.

공유 비밀 `2` 자체를 AES 키로 사용하는 것도 아닙니다. 실제 실행은 공유 비밀과 양측 난수·공개값·통신 기록을 HKDF에 넣어 키를 유도하고, HMAC으로 서로 확인한 뒤 응용 메시지를 주고받습니다.

생각해 볼 질문:

- Alice는 Bob의 개인 지수 b를 받지 않았는데 어떤 값으로 S_A를 계산했나요?
- K_AB는 이 실험 전에 준비한 키입니다. 이번 실행에서 만든 공유 비밀 S와 역할이 어떻게 다른가요?
- 패킷 재생을 멈췄을 때도 상단 실행 결과가 먼저 완료되는 이유는 무엇인가요?

작은 수와 고정 지수는 수학을 보기 쉽게 만든 설정입니다. 실제 보안 강도를 보여주는 예제는 아닙니다.

## 2. Group 14로 바꾸고 실행을 비교하기

**목표:** 계산 원리는 그대로 두고, 값의 크기와 생성 방식이 달라지는 부분을 구분합니다.

1. 모드를 **2048비트 · 표준 그룹 14**로 바꾸고 정상 통신을 실행합니다.
2. 공개값과 패킷의 길이, 단계별 해설, **독립 프로세스** 결과를 확인합니다.
3. 같은 설정으로 한 번 더 실행하고 실행 ID와 공개값·nonce를 비교합니다.
4. 응용 메시지가 Bob에 도착하고 Alice가 응답을 받았는지 확인합니다.

Group 14는 RFC 3526의 2048비트 MODP 매개변수를 사용합니다. 개인 지수는 매번 안전한 난수로 생성하며, 수신 공개값은 범위와 부분군 조건을 검사합니다. 큰 수 모드의 개인 지수와 공유 비밀, 실제 키 원문은 화면과 이벤트 로그에 표시하지 않습니다.

같은 메시지를 다시 보내도 공개값이나 암호문이 달라질 수 있습니다. 새 실행에서 난수와 키를 새로 준비하기 때문입니다. 화면에서 값을 볼 수 없다는 사실과 해당 값이 계산되지 않았다는 것은 서로 다른 의미입니다.

생각해 볼 질문:

- 작은 수 실습과 동일하게 유지되는 계산 단계는 무엇인가요?
- 같은 평문을 여러 번 보내도 암호문이 같을 필요가 없는 이유는 무엇인가요?
- AES 키가 256비트라는 사실만으로 전체 프로토콜이 256비트 보안 강도를 가진다고 할 수 있을까요?

표준 그룹을 사용해도 전체 교육용 설계가 표준 인증 키 교환이 되는 것은 아닙니다. 구현과 보안 가정의 구체적인 범위는 [기술 참고](REFERENCE.md)의 보안상 한계에서 확인하세요.

## 3. 패킷 변조를 관찰하고 중단 지점 찾기

**목표:** 정상 완료와 기대한 검증 거부를 구별하고, 오류가 어느 단계에서 발견되는지 확인합니다.

정상 통신을 한 번 실행한 뒤 다음 시나리오를 하나씩 선택하세요. **보안 실험실** 카드에서 바로 시작할 수도 있습니다.

| 시나리오 | 확인할 기록 | 정상 통신과 다른 점 |
|---|---|---|
| 사전 공유키 불일치 | 인증 실패 `AUTH` | 공개값을 인증 복호화하지 못해 이후 교환을 중단 |
| 암호문 비트 변조 | 인증 실패 `AUTH` | 별도 Eve 프로세스가 바꾼 암호문을 수신자가 거부 |
| 키 확인값 변조 | `KEY_CONFIRM` | 공유 비밀 계산 후에도 상호 키 확인에서 중단 |

각 실험에서 **실행 로그**, **단계별 연산 해설**, **시나리오 판정**을 함께 보세요. 기대한 거부가 확인되면 시나리오 검증은 성공으로 표시될 수 있습니다. 이 경우 응용 메시지 왕복이나 세션 수립까지 성공했다는 뜻은 아닙니다.

생각해 볼 질문:

- AES-GCM 인증과 HMAC 키 확인은 각각 어느 시점에 수행되나요?
- 패킷을 보냈다는 이벤트만으로 상대가 인증에 성공했다고 말할 수 있나요?
- 특정 변조를 한 번 거부했다는 사실이 가능한 모든 공격의 안전성을 증명할까요?

더 비교하고 싶다면 재전송, 잘못된 공개값, 연결 끊김 시나리오의 중단 지점을 살펴보세요. 모든 실험은 앱이 만든 로컬 연결에 한정됩니다.

## 학습 기록 남기기

실행 뒤 **실행 기록 저장**을 눌러 결과와 공개 패킷·이벤트를 JSON으로 보관할 수 있습니다. 예측, 실제 중단 단계, 관련 오류 코드, 그 이유를 한 줄씩 적어 보세요.

이 기록에는 복호화한 응용 메시지가 포함될 수 있습니다. 수업용 예문을 사용하고, 실제 비밀이나 개인정보는 입력하지 마세요. **화면 기록 초기화**는 화면을 지우는 기능이며 디스크에 저장한 로그를 삭제하지 않습니다.

직접 코드를 따라가려면 [기술 참고의 파일 역할과 CLI 안내](REFERENCE.md)를 읽어 보세요. [전체 검증 실행](../README.md#실행-결과-확인)은 수학·암호 연산·실제 TCP·거부 동작을 자동으로 확인하는 다음 실습입니다.
